# Руководство по проекту: прогноз спроса M5 (Walmart, Калифорния)

Документ на русском для автора проекта: что мы делали, зачем и какие получили результаты. Испанские термины даны с переводом. Основные материалы для профессора: `notebooks/m5_forecasting.ipynb`, `reports/informe_ejecutivo.md` и `README.md` (на испанском).

## 1. О проекте

| Параметр | Значение |
|---|---|
| Задача | Прогноз продаж в штуках на **28 дней** по уровню «товар-магазин» |
| Данные | `calendar`, `sales_train_validation`, `sell_prices` (Kaggle, M5 Forecasting - Accuracy) |
| Охват | Штат CA, 4 магазина (CA_1…CA_4), 12 196 рядов |
| Окно истории | `d_1500 … d_1913` (414 дней) |
| Обучение / валидация | `d_1500 … d_1885` / `d_1886 … d_1913` (последние 28 дней) |
| Модель | LightGBM, 500 деревьев, целевая функция Tweedie |
| Метрики | RMSE и MAE (WRMSSE не считали из-за срока) |
| Срок | Сначала неделя, затем сокращён до двух дней |

## 3. Данные и память

### 3.1 Что содержат таблицы

| Таблица | Размер | Смысл |
|---|---|---|
| `sales_train_validation` | 30 490 × 1 919 | Одна строка = один ряд «товар + магазин» (3 049 товаров × 10 магазинов). Столбцы `d_1…d_1913` = продажи в штуках по дням. Формат *wide* (широкий) |
| `calendar` | 1 969 × 14 | Дата, день недели, месяц, события, SNAP по штатам |
| `sell_prices` | 6 841 121 × 4 | Цена по связке магазин + товар + неделя |

### 3.2 Ключи объединения

| Связь | Ключ | Комментарий |
|---|---|---|
| calendar ↔ продажи | `d` (после `melt` используем число `d_num`) | `d_1500 → 1500` |
| calendar ↔ sell_prices | `wm_yr_wk` | Цена задана по неделям, не по дням |

### 3.3 Память: было → стало

| Этап | calendar | sales | sell_prices | Всего |
|---|---|---|---|---|
| Исходно | 0,3 МБ | 448,2 МБ | 318,1 МБ | **766,6 МБ** |
| После downcasting | 0,2 | 96,3 (−79%) | 252,9 (−21%) | 349,4 МБ |
| После `category` | 0,1 | 94,4 | 58,8 | ≈ 153 МБ |
| Длинная таблица `largo` (5 049 144 строки) | | | | 173,8 МБ |

**Логика:**
- *Downcasting* = замена `int64` на самый маленький тип, в который влезают все значения (`np.iinfo`), и `float64` на `float32`.
- `category` выгоден, когда уникальных значений мало, а строк много. Для `id` и `d` (уникальны в каждой строке) он не нужен.
- После `melt` `id` стоит перевести в `category`: он повторяется 414 раз.

**Ключевой вывод:** во всех строках без цены продаж = 0. Это «товара ещё нет в продаже», а не «нет спроса».

## 6. Признаки (фаза 2)

| Группа | Признаки | Как считали |
|---|---|---|
| Календарь | `dia_semana`, `dia_mes`, `dias_hasta_fin_mes`, `fin_de_semana`, `month`, `snap`, `tiene_evento`, `event_type_1` | Из даты и calendar |
| Лаги | `lag_28`, `lag_29`, `lag_35`, `lag_42` | `groupby("id").shift(k)` |
| Окна | `media_7`, `std_7`, `media_28`, `std_28` | Сначала `shift(28)`, потом `rolling` |
| Цена | `sell_price`, `precio_rel_dept`, `cambio_precio_1s`, `cambio_precio_4s`, `descuento_pct`, `en_descuento` | Цена известна заранее, сдвиг не нужен |
| Категории | `dept_id`, `cat_id`, `store_id` | Тип `category` |

**Почему лаги ≥ 28:** мы прогнозируем сразу 28 дней вперёд, и для дня *t* известны продажи только до *t-28*. Это прямая стратегия (*Direct Forecasting*).

**Почему утечки нет (проверка 2.2.3):** (1) дни внутри ряда идут подряд, значит, сдвиг на 28 строк равен сдвигу на 28 дней; (2) ручной расчёт `lag_28` и `media_7` совпал с кодом. Пропуски в начале рядов не заполняли: LightGBM их понимает, а заполнение глобальным средним было бы утечкой.

**Что не включили в модель:**

| Признак | Причина |
|---|---|
| `year`, `d_num`, `date` | Дерево не умеет продолжать тренд, оно «запомнит момент» |
| `item_id`, `id` | 3 049 значений, риск переобучения |
| `event_name_1/2` | ~30 названий по 1-2 появления |
| `state_id` | Константа (только CA) |

Доля пропусков в начале рядов: от 6,8% (`lag_28`) до 13,4% (`media_28`).

## 7. Моделирование (фаза 3)

### 7.1 Валидация

| Правило | Как соблюдено |
|---|---|
| Строго по времени | Train `d_1500…d_1885`, val `d_1886…d_1913` |
| Без случайного K-Fold | Один out-of-time срез |
| Без утечки | Лаги и окна на `shift(28)`; бейзлайны используют только данные до `d_1885` |
| Без подгонки под валидацию | 500 деревьев фиксированно, early stopping не использовали |

Строк: train 4 667 377, validation 341 488.

### 7.2 Результаты

| Модель | RMSE | MAE |
|---|---|---|
| Сезонный наивный | 2,8315 | 1,3244 |
| Скользящее среднее 28 дней (лучший бейзлайн) | 2,2604 | 1,1070 |
| Ноль | 3,8650 | 1,4764 |
| **LightGBM** | **2,1613** | 1,1097 |

LightGBM лучше лучшего бейзлайна на **4,4% по RMSE**, по MAE равен (−0,2%).

### 7.3 Детализация

| Срез | RMSE LGBM | RMSE media28 | Вывод |
|---|---|---|---|
| FOODS | 2,5719 | 2,7303 | Основной выигрыш (−5,8%) |
| HOBBIES | 1,9469 | 1,9497 | Почти равны |
| HOUSEHOLD | 1,5744 | 1,6113 | Небольшой выигрыш |
| Неделя 1 | 2,2655 | 2,2829 | −0,8% |
| Неделя 2 | 2,2068 | 2,2626 | −2,5% |
| Неделя 3 | 2,1408 | 2,2853 | −6,3% |
| Неделя 4 | 2,0245 | 2,2099 | −8,4% |

- Смещение: среднее прогноза 1,4741 против факта 1,4764 (≈ −0,2%).
- Преимущество растёт с горизонтом. Это **согласуется** с гипотезой, что в первые дни признаки прямой стратегии «устарели» (последние 27 известных дней не используются, а бейзлайн их использует). Это не доказано.
- Гипотеза про Tweedie (среднее вместо медианы, поэтому MAE не улучшился) **не проверена**.

## 9. Ошибки по ходу работы и что из них вынесли

| Ситуация | Что было не так | Как исправили |
|---|---|---|
| Удаление строк без цены | Ячейка не выполнилась до разделов 2.1-2.3, лаги считались с лишними строками. По `describe().count` я ошибочно «подтвердила» удаление: он не считает `NaN` | *Restart & Run All*, проверка по числу строк (4 667 377 + 341 488 = 5 008 865) |
| SNAP и «начало месяца» | Эффекты полностью перекрываются (SNAP = дни 1-10) | В отчёте пишем об этом ограничение, не приписываем эффект SNAP |
| Замена текста в 4.2 | Заменили не то предложение, пропал рост в длинные выходные | Вернули, убрали дубль про Religious |
| Среднее National без Christmas | Я сначала оценила ≈ −0,5% | Пересчитано: ≈ +1% |
| Пустые файлы | `models/lgbm_model.txt` (0 байт), `reports/informe_ejecutivo.md` (0 байт) | Первый удалили, второй заполнили |

**Практические выводы:**
- Прежде чем верить выводу, проверять суммы (строки, `assert`).
- В ноутбуке запускать всё через *Restart & Run All*, а не ячейками вразнобой.
- Не подбирать гиперпараметры по валидации: оценка станет слишком оптимистичной.

## 12. Глоссарий

| Термин (es) | Перевод | Смысл |
|---|---|---|
| *wide* / *long* | широкий / длинный формат | Время в столбцах / время в строках |
| *melt* (despivotado) | «расплавить» таблицу | Из wide в long |
| *downcasting* | понижение разрядности | Более компактный числовой тип |
| *category* | категориальный тип | Хранит уникальные тексты один раз |
| *lag* (rezago) | лаг | Значение ряда k дней назад |
| *ventana móvil* | скользящее окно | Среднее/std за последние w дней |
| *fuga de datos* (*data leakage*) | утечка данных | Использование будущего при обучении |
| *validación out-of-time* | валидация вне времени обучения | Валидация строго после обучения |
| *baseline* | бейзлайн | Простая модель для сравнения |
| *demanda intermitente* | прерывистый спрос | Много нулевых дней |
| *sobreajuste* (*overfitting*) | переобучение | Модель запоминает шум |
| *colinealidad* | коллинеарность | Один признак однозначно определяет другой |
| RMSE | корень из среднего квадрата ошибки | Сильнее штрафует большие промахи |
| MAE | средняя абсолютная ошибка | Все ошибки линейно |
| WRMSSE | взвешенный масштабированный RMSE | Официальная метрика M5 |
| *Tweedie* | распределение Твиди | Для неотрицательных данных с множеством нулей |
| *feature importance* (gain) | важность признаков | Суммарное улучшение потерь за счёт признака |
| *quiebre de stock* / *sobrestock* | дефицит / излишек запаса | Недопрогноз / перепрогноз |
